# Сценарии и Раннеры Верификации (Smoke & Quality Runners)

Проект содержит три специализированных сценария автоматического тестирования и оценки качества, которые проверяют поведение агентов, утечку контекста, корректность OCR, а также логику продолжения и слияния документов. 

Все запуски сценариев записывают метаданные исполнения, сгенерированные артефакты и вердикты оценок в локальный реестр SQLite.

---

## 1. Смоук-раннер OCR и исследований (`ocr_research_smoke_runner.py`)

Расположен в [`ocr_research_smoke_runner.py`](../scripts/ocr_research_smoke_runner.py). Этот скрипт предназначен для быстрой проверки доменных границ пайплайна.

### Каталог сценариев:
- **`web_search_off_standard_pipeline`**: Проверяет, что пайплайн успешно выполняется в стандартном режиме, когда веб-поиск выключен, и исследовательский агент не делает запросов.
- **`web_search_on_researcher_boundary`**: Проверяет, что при включенном поиске планировщик получает результаты поиска, а писатель — только структурированный план, не имея прямого доступа к сырым ответам краулера.
- **`reference_attachment_planner_only`**: Проверяет, что вложения (справочные материалы) попадают только к планировщику, изолируя писателя от утечки "сырых" маркеров контекста.
- **`uploaded_continuation_source`**: Проверяет разделение входящего markdown-файла на секции продолжения и автоматическую генерацию шаблона.
- **`mistral_ocr_direct`**: Напрямую тестирует интеграцию с Mistral OCR (требует реальный API-ключ, генерирует PDF с уникальным маркером и проверяет его распознавание).
- **`real_llm_web_research`**: Сквозной тест пайплайна с использованием реального поиска и реальных LLM-моделей для планирования и написания.

### Использование:
Запуск конкретного сценария:
```bash
poetry run python scripts/ocr_research_smoke_runner.py <scenario_id>
```
*Например: `poetry run python scripts/ocr_research_smoke_runner.py web_search_off_standard_pipeline`*

Логи записываются в `exports/_smoke_ocr_research/<timestamp>/<scenario_id>/stage_log.jsonl` и заносятся в реестр SQLite.

## 2. Раннер качественной оценки OCR (`ocr_research_quality_eval_runner.py`)

Расположен в [`ocr_research_quality_eval_runner.py`](../scripts/ocr_research_quality_eval_runner.py). Оценивает точность распознавания сложных элементов (формул LaTeX, табличной структуры, ссылок) после обработки через OCR.

### Каталог сценариев:
- **`simple_latex_paper`**: Компилирует тестовую статью с простыми формулами LaTeX, прогоняет через Mistral OCR и проверяет полноту сохранения формул.
- **`complex_math_table_attribution`**: Генерирует документ со сложной математической матрицей, таблицей данных и списком литературы, верифицируя точность парсинга таблиц и правильность извлечения цитат.

Каждый прогон создает запись в таблице `evaluations` реестра SQLite со статусом `pending` (ожидает ручного ревью) и ссылкой на детальный markdown-отчет оценки.

### Использование:
```bash
poetry run python scripts/ocr_research_quality_eval_runner.py <scenario_id>
```

## 3. Смоук-раннер продолжения документов (`continuation_smoke_runner.py`)

Расположен в [`continuation_smoke_runner.py`](../scripts/continuation_smoke_runner.py). Тестирует различные режимы продолжения и слияния документов.

### Каталог сценариев:
- **`creative_continuation`**: Продолжение художественного рассказа. Проверяет бесшовное слияние без дублирования экспозиций или ввода служебных заголовков.
- **`creative_bridge`**: Проверка соединения/замены хвоста при достижении жесткого финала (closed ending).
- **`school_revision`**: Редактирование школьного эссе "поверх" текста (`revise_in_place`), сохраняя стиль и голос ученика.
- **`academic_references`**: Академическое продолжение отчета RGR с LaTeX формулами, требующее объединения новых источников в единую библиографию в конце документа.
- **`technical_continuation`**: Продолжение README-файла, проверяющее сохранение технического стиля без скатывания в структуру академической статьи.

### Использование:
```bash
poetry run python scripts/continuation_smoke_runner.py <scenario_id>
```

## Интеграция с реестром оценок

Каждый запуск раннера фиксируется в базе данных:
1. В таблице `runs` создается запись типа `smoke` или `quality` со статусом выполнения.
2. В таблице `evaluations` сохраняется вердикт проверки (тип `smoke` или `semi_manual` для качественной оценки) со статусом `passed`, `failed` или `pending`.
3. Все сопутствующие файлы (лог смоука, сгенерированный PDF-отчет) регистрируются как диагностические записи в `artifacts`.
