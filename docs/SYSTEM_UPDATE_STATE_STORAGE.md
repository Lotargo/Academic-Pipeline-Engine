# System Update: State, Storage, Streaming

Дата: 2026-06-12

Этот документ фиксирует архитектурное направление для следующего этапа развития Academic Pipeline Engine. Он не является баг-репортом и не описывает текущие дефекты UI. Цель документа - отделить стратегические решения по состоянию, хранению, очередям и стримингу от оперативных задач.

## Контекст

Текущая реализация уже имеет рабочую FSM-оркестрацию, LLM abstraction, review loop, DOCX export и UI-мониторинг. При этом состояние выполнения пока слишком близко к in-memory runtime backend-процесса. Это создает ограничения:

- refresh страницы зависит от текущего состояния процесса;
- live-прогресс требует аккуратного SSE/polling поведения;
- история, настройки и артефакты пока не имеют полноценного долговременного слоя;
- несколько пользователей или несколько параллельных запусков будут усложнять текущую модель;
- отмена, retry, восстановление и аудит должны опираться на устойчивый `run_id`, а не на глобальное состояние.

## Принятое направление

Рекомендуемая целевая схема:

```text
Frontend
  -> FastAPI API
  -> PostgreSQL: durable state, configs, document library, metadata
  -> Redis: queue, locks, active run state, SSE events, short-lived logs
  -> Worker/Orchestrator
  -> Filesystem or S3-compatible storage: DOCX/PDF/preview artifacts
```

## Роли компонентов

### PostgreSQL

Используется как долговременный источник истины:

- пользователи и рабочие пространства;
- настройки агентов и версии конфигураций;
- pipeline runs;
- секции документа;
- статусы FSM и финальные результаты;
- metadata библиотеки документов;
- ссылки на DOCX/PDF/preview artifacts;
- audit/history.

Причина выбора: структура проекта хорошо ложится на реляционную модель, нужны связи `run -> sections -> events -> artifacts`, фильтрация, пагинация, транзакции и надежная история. `JSONB` можно использовать для гибких полей конфигурации и provider-specific payloads.

### Redis

Используется как быстрый слой исполнения:

- очередь задач;
- lock на активный запуск;
- active run state;
- stream событий по `run_id`;
- short-lived token deltas;
- short-lived logs;
- cancel flags;
- TTL для временных данных;
- rate limiting.

Redis может временно закрыть часть потребностей вместо Kafka и даже части document-state storage, но не должен быть единственным долговременным архивом, если потеря истории и документов недопустима.

### Kafka

На текущем этапе не является обязательной зависимостью.

Kafka имеет смысл только при появлении требований:

- много независимых worker-групп;
- большой поток событий;
- долговременный immutable event log;
- сложная аналитика событий;
- масштабирование за пределы одного приложения.

До этого Redis Streams или job queue дают достаточную устойчивость при меньшей операционной сложности.

### Secrets

API-ключи и секреты не должны храниться в Redis как обычные значения.

Допустимые варианты:

- local/dev: `.env`, OS keyring или существующий локальный secrets layer;
- production: encrypted secrets в БД или внешний secret manager;
- шифрование значений перед записью;
- запрет на запись полных ключей в logs/events;
- раздельная политика хранения для secrets и обычных настроек.

## PostgreSQL vs MongoDB

Выбор по умолчанию: PostgreSQL.

Причины:

- строгие связи между users, runs, sections, artifacts и configs;
- транзакции;
- удобные индексы и пагинация;
- зрелые миграции через Alembic;
- хорошая база для админки, отчетов и audit trail;
- `JSONB` покрывает часть гибкости MongoDB.

MongoDB может быть уместна, если основной объект системы станет большим слабоструктурированным JSON-документом с постоянно меняющейся схемой. Для текущей модели Academic Pipeline Engine это менее предпочтительно: сначала проще, но позже сложнее контролировать форму данных, индексы, миграции и консистентность.

## Что улучшится

После введения устойчивого state/storage/event слоя:

- refresh страницы сможет восстанавливаться по `run_id`;
- live stream не будет зависеть от глобального in-memory dict;
- история запусков станет нормальной библиотекой документов;
- настройки можно будет версионировать;
- отмена и retry станут надежнее;
- UI сможет читать последние события после reconnect;
- появится база для нескольких пользователей;
- logs и token deltas можно будет хранить с TTL;
- frontend сможет использовать пагинацию и виртуализацию поверх нормальных API.

## Что не ускорится напрямую

PostgreSQL, Redis или Kafka не делают сам LLM-провайдер быстрее.

Скорость ответа модели зависит от:

- выбранной модели;
- размера prompt/context;
- max output;
- сети и latency провайдера;
- streaming support;
- retry/circuit breaker;
- параллелизма секций;
- объема reviewer-проверок.

Архитектура хранения улучшает устойчивость и perceived responsiveness, но реальное ускорение LLM требует отдельной оптимизации prompt flow и provider strategy.

## UI-оптимизация

Оптимизация frontend нужна точечно:

- history/document library: server-side pagination;
- logs: virtualization;
- long markdown preview: memoization by section;
- section rendering: avoid full document re-render on each token delta;
- sidebar/history selection: single-source state;
- polling/SSE reconnect: run-scoped subscription.

Эти задачи следует выполнять по мере роста объема данных, а не заранее во всех местах.

## Ближайший практичный этап

До перехода на внешние зависимости можно подготовить код так, чтобы миграция была мягкой:

1. Ввести `run_id` как обязательную сущность выполнения.
2. Убрать зависимость UI от единственного глобального `current_run`.
3. Описать интерфейс `RunStore`.
4. Описать интерфейс `EventBus`.
5. Описать интерфейс `JobQueue`.
6. Оставить in-memory/file-backed реализации как dev fallback.
7. Перевести SSE на `/api/runs/{run_id}/events`.
8. Разделить durable state и transient events на уровне интерфейсов.

## Целевой принцип

Система должна быть способна работать в простом локальном режиме без обязательных внешних сервисов, но иметь ясные adapter interfaces для Redis/PostgreSQL.

Это позволит сначала стабилизировать доменную модель, а потом подключать внешние зависимости без переписывания UI, orchestrator и agent layer.
