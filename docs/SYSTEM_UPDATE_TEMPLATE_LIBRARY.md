# System Update: Template Library and Runtime Planning

Date: 2026-06-12

Related document: [SYSTEM_UPDATE_STATE_STORAGE.md](./SYSTEM_UPDATE_STATE_STORAGE.md)

This document records the next architectural decision for Academic Pipeline Engine: document structure must not be treated as a single global pipeline shape. The system needs reusable document templates, user custom templates, and an automatic runtime template mode.

This is not a bug report. It is a system-design update linked to the future PostgreSQL/Redis storage plan.

## Problem

The current `pipeline.sections` configuration has too many responsibilities:

- it is the default document outline;
- it is the active structure for the current generation;
- it is edited through the settings UI as a custom rule constructor;
- it implicitly acts as the only available document template.

This creates a serious prompt-routing problem. If the configured structure is academic, for example `theory / calculation / conclusion`, and the user asks for a non-academic document such as "write an article about daisies blooming in a field", the agent may still force the request into the academic section structure.

The issue is not model intelligence. The system is giving the model a mismatched structural contract.

## Decision

Introduce a document-template layer before drafting.

The pipeline should distinguish:

- saved templates;
- the active template selected for a run;
- temporary runtime templates generated by a planner agent;
- user custom templates edited in settings;
- prompt manifests attached to each template.

## Core Concepts

### DocumentTemplate

A reusable template definition.

Suggested fields:

```yaml
id: academic_arxiv
name: Academic Article (arXiv style)
description: Structured research-style article with abstract, methods, analysis, conclusion.
category: academic
language_policy: auto
sections:
  - name: abstract
    title: Abstract
    instruction: Summarize the objective, method, and key claim.
  - name: introduction
    title: Introduction
    instruction: Establish context, motivation, and scope.
prompt_manifest:
  writer_role: Academic research writer
  reviewer_role: Academic peer reviewer
  style_contract:
    tone: formal
    structure: research article
  review_rubric:
    required:
      - coherent research claim
      - consistent terminology
    forbidden:
      - poem/stanza critique
      - school essay grading criteria
```

### TemplateLibrary

The collection of saved templates available to the user and selector.

Before PostgreSQL, this can be file-backed:

```text
config/document_templates.yaml
```

After PostgreSQL, it becomes persistent storage with:

- template ids;
- versions;
- owners;
- visibility;
- categories;
- timestamps;
- migration history.

### RuntimeTemplate

A template snapshot used for exactly one generation run.

Runtime templates may come from:

- a saved template;
- a user custom template;
- auto mode planner output.

Runtime templates should be stored with the run metadata later, but auto-generated runtime templates should not automatically pollute the saved template library.

### PromptManifest

A template-specific prompt contract for agents.

The template shape alone is not enough. If a poem template changes only the section list, but the Writer and Reviewer still use academic article prompts, the Writer may add chapters/methodology and the Reviewer may reject because there is no methodology or conclusion. This is the same class of mismatch as forcing a flower article into `theory / calculation / conclusion`.

Each template must therefore provide a prompt manifest that defines how agents should behave for that document type.

Suggested fields:

```yaml
prompt_manifest:
  planner_role: Template planner for the selected document type
  writer_role: Writer role for this document type
  reviewer_role: Reviewer role for this document type
  writer_task: What the writer must optimize for
  reviewer_task: What the reviewer must validate
  style_contract:
    tone: formal | lyrical | explanatory | narrative | neutral
    structure: sections | stanzas | paragraphs | report
    allowed_devices:
      - metaphor
      - formula
      - bullet list
    forbidden_devices:
      - unsupported numeric claims
      - academic methodology section
  review_rubric:
    required:
      - document-type-specific requirements
    optional:
      - nice-to-have qualities
    forbidden:
      - checks that do not apply to this template
  output_constraints:
    markdown_allowed: true
    latex_allowed: false
    headings_allowed: false
```

Examples:

For `academic_arxiv`, the manifest may require abstract, method clarity, terminology consistency, citations placeholders, equations, and formal tone.

For `poem`, the manifest should allow imagery, rhythm, stanza structure, and ambiguity. It must explicitly forbid academic-review checks such as missing methodology, missing formulas, missing conclusion, or lack of thesis statement unless the user requested a critical essay about poetry.

For `freeform_article`, the manifest should prefer readable prose, coherent flow, and factual consistency, but should not require H2/H3 academic sectioning.

### RuntimePromptManifest

A prompt manifest snapshot used for one run.

Runtime prompt manifests may come from:

- a saved template manifest;
- a user custom template manifest;
- auto mode planner output.

Like `RuntimeTemplate`, an auto-generated `RuntimePromptManifest` should be temporary by default and stored only with the run metadata unless the user explicitly saves it.

### TemplateSelector

The component that decides which template to use.

Modes:

- `fixed`: use the explicitly selected saved template;
- `custom`: use the current settings UI structure;
- `auto`: ask a planner agent to create a temporary runtime template from the user prompt.

### PlannerAgent

A lightweight pre-drafting agent responsible for template planning, not content drafting.

In `auto` mode it should produce:

- document type;
- section list;
- section purposes;
- style constraints;
- expected tone;
- prompt manifest for Writer and Reviewer;
- any necessary warnings about mismatch between user request and available templates.

The planner output is consumed by the orchestrator and then discarded unless the user explicitly saves it as a reusable template.

## Initial Built-In Templates

Recommended starter set:

- `academic_arxiv`: scientific article, arXiv-like structure;
- `academic_report`: student/report style document;
- `essay`: thesis-driven essay;
- `school_composition`: simple composition with introduction/body/conclusion;
- `poem`: poem/stanza-oriented structure;
- `freeform_article`: general article without heavy academic apparatus;
- `technical_note`: concise technical explanation;
- `custom_current`: current settings UI structure.

Each built-in template must include both:

- `sections`;
- `prompt_manifest`.

Adding only sections is incomplete and should be treated as invalid template configuration.

## Relationship to PostgreSQL

PostgreSQL is not required to start this work.

Before PostgreSQL:

- templates can be stored in YAML;
- user edits can update the existing config;
- runtime templates can live only in memory and metadata JSON.
- prompt manifests can be stored next to templates in YAML.

After PostgreSQL:

- saved templates should move to database tables;
- custom user templates should be versioned;
- prompt manifests should be versioned with their templates;
- each generated run should store the runtime template snapshot;
- each generated run should store the runtime prompt manifest snapshot;
- document library entries should reference the template used.

Suggested future tables:

```text
document_templates
document_template_versions
document_template_sections
document_template_prompt_manifests
pipeline_runs.template_snapshot
pipeline_runs.prompt_manifest_snapshot
```

## Relationship to Redis

Redis is not required for template selection itself.

Redis becomes useful when template planning is part of a durable async run:

- store planner status;
- stream planner events;
- allow reconnect to an active planning/drafting run;
- keep short-lived runtime template state by `run_id`;
- keep short-lived runtime prompt manifest state by `run_id`;
- coordinate workers.

The template layer should be designed now so Redis can later back active runtime state without changing the orchestrator contract.

## Proposed Flow Before External Dependencies

```text
User prompt
  -> TemplateSelector
     -> fixed/custom: load saved structure
     -> auto: PlannerAgent creates RuntimeTemplate + RuntimePromptManifest
  -> Orchestrator receives RuntimeTemplate.sections + RuntimePromptManifest
  -> Writer drafts using RuntimeTemplate + RuntimePromptManifest + document plan
  -> Reviewer checks against RuntimeTemplate + RuntimePromptManifest constraints
  -> Metadata records template id, runtime template snapshot, and prompt manifest snapshot
```

## Proposed Flow After PostgreSQL and Redis

```text
User prompt
  -> API creates run_id in PostgreSQL
  -> Redis queue dispatches planning job
  -> PlannerAgent creates RuntimeTemplate + RuntimePromptManifest
  -> PostgreSQL stores runtime template and prompt manifest snapshots
  -> Redis streams planning/drafting/review events
  -> Worker drafts/reviews using runtime template and prompt manifest
  -> Document library stores final artifact metadata
```

## Implementation Order

Recommended order before adding external services:

1. Add `DocumentTemplate`, `PromptManifest`, `RuntimeTemplate`, and `RuntimePromptManifest` Pydantic models.
2. Add file-backed `TemplateLibrary`.
3. Move existing `pipeline.sections` into `custom_current` compatibility mode.
4. Add built-in templates in `config/document_templates.yaml`.
5. Add `template_mode` and `template_id` to config/API run payload.
6. Add `TemplateSelector`.
7. Add `PromptManifestResolver` to compose base agent prompts with template-specific manifest instructions.
8. Add `PlannerAgent` for `auto` mode.
9. Store the selected runtime template and runtime prompt manifest in run metadata.
10. Update UI settings so "Document Chapters & Structure" is clearly a template editor, not the global pipeline truth.

## Guardrails

- A user prompt must not be forced into an incompatible saved template unless the user explicitly selected that template.
- Auto-generated templates must be temporary by default.
- The planner should not write the document content.
- The writer should receive the runtime template as binding structure.
- The writer should receive the runtime prompt manifest as its document-type-specific behavior contract.
- The reviewer should evaluate against the runtime template and runtime prompt manifest, not against a hardcoded academic outline.
- A reviewer must not apply requirements from a different document type.
- A writer must not introduce headings, chapters, formulas, citations, or methodology sections unless allowed by the active manifest or requested by the user.
- Saved templates should have stable ids and versioned sections once PostgreSQL is introduced.

## Architectural Link

This update complements [SYSTEM_UPDATE_STATE_STORAGE.md](./SYSTEM_UPDATE_STATE_STORAGE.md):

- PostgreSQL will eventually persist template library, versions, user ownership, and runtime template snapshots.
- Redis will eventually support active run state, planning/drafting events, and worker coordination.
- PostgreSQL will also persist prompt manifests and prompt manifest snapshots.
- Redis will also support active runtime prompt manifest state for reconnectable runs.
- The template and manifest layers can be implemented now with file-backed adapters, then moved behind PostgreSQL/Redis adapters later.
